# 3Lines 전반 개선 프로그램 및 1차 런타임 정확성·에너지 설계

## 1. 목적

3Lines를 비판적 검토자 관점에서 반복 평가하고, 측정 가능한 근거에 따라
정확성, 배터리 사용량, 성능, UI/UX, 접근성, 구조, 출시 품질을 점진적으로
개선한다. 한 번에 전면 재작성하지 않고, 독립적으로 검증 가능한 개선 루프를
순서대로 수행한다.

이 문서는 전체 개선 프로그램의 공통 루브릭과 첫 번째 하위 프로젝트인
알림·홈 위젯 런타임 정확성 및 백그라운드 에너지 개선을 확정한다.

현재 확인된 주요 위험은 다음과 같다.

1. `timezone` 데이터 초기화 후 `tz.local`을 기기 시간대로 지정하지 않아 알림이
   기본 UTC를 기준으로 예약될 수 있다.
2. Darwin 알림 플러그인 초기화가 권한 요청 옵션을 켜고 있으며 앱 첫 프레임 뒤
   무조건 실행된다. 사용자가 알림을 활성화하기 전에 권한 팝업이 뜰 수 있다.
3. 일일 알림 예약이 모든 알림 ID를 취소하므로 스트릭 및 주간 회고 알림까지
   제거한다.
4. 오늘 기록이 이미 있으면 스마트 일일 알림이 모든 예약을 취소하고 다음 날
   일일 예약을 만들지 않는다.
5. 기록 저장 뒤 설정 화면의 `autoDispose` 상태를 읽어 알림 설정을 얻는다.
   설정 화면을 열지 않은 일반적인 흐름에서는 값이 아직 없어 재예약이 생략될 수
   있다.
6. 기록 저장은 저널 변경 이벤트와 직접 호출 양쪽에서 홈 위젯 동기화를 요청해
   동일한 DB 조회, 공유 저장소 쓰기, 플랫폼 업데이트가 중복될 수 있다.
7. Android 홈 위젯의 `updatePeriodMillis`가 30분이어서 상태 변화가 거의 없는
   마이크로 저널 앱이 하루 최대 48회의 주기 업데이트를 요청한다.
8. 현재 테스트는 Controller가 실제 알림 구현을 상속한 Fake로 대체하므로 알림
   ID 간 취소 간섭, 시간대 초기화, 실제 예약 날짜 계산을 검증하지 않는다.

## 6. 루프 1 아키텍처

### 6.1 `DeviceTimeZoneResolver`

플랫폼에서 기기 IANA 시간대 식별자를 얻는 작은 경계다. 구현은
`flutter_timezone: ^5.1.0`의 `FlutterTimezone.getLocalTimezone()`을 사용한다.
이 버전은 Dart 3.4 이상과 Java 17을 요구하며 현재 프로젝트의 Dart 3.9 이상,
Java 17 설정과 호환된다.

시간대 데이터 초기화 후 resolver가 반환한 식별자로 `tz.getLocation`과
`tz.setLocalLocation`을 호출한다. 알 수 없는 식별자이거나 플랫폼 호출이 실패하면
UTC로 조용히 예약하지 않는다. 초기화를 실패 처리하고 사용자가 다시 시도할 수
있게 한다. 잘못된 시각의 알림보다 명시적 실패가 안전하다.

### 6.2 `NotificationPlatform`

`FlutterLocalNotificationsPlugin`을 감싸는 저수준 어댑터다. 다음 책임만 가진다.

- 권한을 요청하지 않는 플러그인 초기화
- 사용자가 알림을 활성화할 때만 플랫폼 권한 요청
- 지정 ID와 날짜의 `zonedSchedule`
- 지정 ID 하나의 취소

Darwin 초기화의 alert, badge, sound 권한 요청 옵션은 모두 `false`다. 예약 메서드는
기존 같은 ID를 새 요청으로 교체하며, 다른 ID를 선행 취소하지 않는다.

### 6.3 `NotificationService`

알림 ID와 날짜 계산을 소유한다.

- `scheduleDailyReminder`: 일일 알림 ID만 생성·교체
- `scheduleStreakAtRiskReminder`: 스트릭 알림 ID만 생성·교체
- `scheduleWeeklyRetrospectiveReminder`: 주간 알림 ID만 생성·교체
- `cancelDailyReminder`, `cancelStreakAtRiskReminder`,
  `cancelWeeklyRetrospectiveReminder`: 해당 ID만 취소
- `cancelAllReminders`: 사용자가 기능을 끌 때만 세 ID를 취소

일일 및 스트릭 예약은 `startTomorrow` 입력을 받는다. 오늘 기록이 있으면 다음 날,
없으면 아직 지나지 않은 오늘 시각 또는 다음 날을 첫 예약으로 정한다. 반복 규칙은
각각 시간, 요일과 시간으로 유지한다.

`scheduleDailyReminder`는 더 이상 `cancelAllReminders`를 호출하지 않는다. 주간 회고
예약은 일일 시간 변경이나 저널 저장과 독립적으로 보존된다.

### 6.4 `ReminderCoordinator`

설정과 기록 이벤트에 따른 예약 정책의 유일한 진입점이다.

- 활성화: 권한 요청 → 현재 기록·스트릭 확인 → 세 예약 적용 → 성공 후 설정 저장
- 비활성화: 세 예약 취소 성공 → 설정 저장
- 시간 변경: 현재 기록·스트릭에 맞춰 일일·스트릭 예약 교체 → 성공 후 시간 저장
- 기록 저장: `SettingsRepository`에서 저장된 알림 설정을 직접 읽고, 활성 상태라면
  일일·스트릭 알림의 첫 발생을 다음 날로 교체
- 저널 변경 재조정: 저장·가져오기·삭제 후 현재 오늘 기록과 스트릭을 다시 읽어
  일일·스트릭 예약을 현재 데이터와 일치시킴

Controller는 `SettingsController`의 일시적인 UI 상태를 다른 Controller에서 읽지
않는다. Coordinator는 저장소를 진실의 원천으로 사용한다. 주간 회고 시각은 일일
알림 시간과 무관하므로 시간 변경과 기록 저장에서 다시 만들거나 취소하지 않는다.

동시에 들어온 정책 변경은 Coordinator 내부에서 순서대로 처리한다. 앞선 비동기
작업의 늦은 완료가 사용자의 최신 설정을 덮어쓰지 못하게 한다.

Coordinator는 변경 전에 DB에 저장된 설정으로 기존 예약 계획을 구성한다. 새 계획
적용 중 일부 플랫폼 호출이 실패하면 기존 계획을 최선 노력으로 다시 적용한다.
복원까지 실패하면 UI와 DB는 기존 설정을 유지하고 두 실패를 모두 기록한다. 플랫폼
예약 여러 개를 진정한 트랜잭션으로 바꿀 수는 없으므로, 실패를 성공으로 표시하지
않고 다음 사용자 동작에서 저장된 계획으로 다시 조정하는 것이 일관성 경계다.

### 6.5 `WidgetSyncService`

위젯 스냅샷에 값 동등성을 부여하고 마지막 성공 스냅샷을 보관한다.

- 동기화가 진행 중이면 새 플랫폼 업데이트를 즉시 중복 실행하지 않는다.
- 진행 중 상태가 끝났을 때 변경 요청이 추가로 있었다면 최신 DB 상태로 정확히 한
  번 더 수행한다.
- 새 스냅샷이 마지막 성공 스냅샷과 같으면 공유 저장소 쓰기와 네이티브 위젯
  업데이트를 생략한다.
- 실패한 스냅샷은 성공 캐시에 기록하지 않아 다음 요청에서 재시도한다.

앱 시작 및 재개 동기화는 유지한다. 저널 변경 이후에는
`journalChangesProvider`를 구독하는 `WidgetBootstrap`만 동기화를 호출한다.
`TodayController.save`의 직접 위젯 호출은 제거한다.

같은 저널 변경 구독에서 ReminderCoordinator의 재조정도 요청한다. 따라서 Today
저장뿐 아니라 가져오기, 개별 삭제, 전체 삭제도 오늘 기록 여부와 알림 계획을 다시
일치시킨다. Controller가 다른 화면의 UI provider 상태를 참조하는 후속 작업은
제거한다.

### 6.6 Android 네이티브 위젯

`updatePeriodMillis`를 1,800,000ms에서 86,400,000ms로 변경하여 요청 주기를 하루
최대 한 번 수준으로 낮춘다. 앱 시작, 재개, 기록 변경 시의 명시적 업데이트는
그대로 유지된다.

네이티브 provider는 저장된 `date`가 기기 현지 날짜와 같은지 확인한다. 날짜가
지났다면 이전 날의 `is_completed`와 `emotion`을 오늘 상태로 재사용하지 않고
미작성 상태와 기본 질문을 표시한다. 따라서 주기 업데이트가 자정 직후 정확히
실행되지 않아도 과거 완료 상태를 무기한 노출하지 않는다.

## 7. 데이터 흐름

### 7.1 앱 시작

1. Bootstrap은 온보딩과 잠금에 필요한 설정만 먼저 읽는다.
2. 알림 플러그인과 시간대 데이터는 초기화하지 않는다.
3. 첫 프레임 뒤 WidgetBootstrap이 위젯 스냅샷을 한 번 동기화한다.
4. 사용자가 알림 기능을 사용하기 전에는 권한 요청이나 알림 플랫폼 호출이 없다.

### 7.2 알림 활성화

1. Settings 화면이 Coordinator에 활성화를 요청한다.
2. Coordinator가 명시적으로 알림 권한을 요청한다.
3. 권한이 승인되면 기기 시간대를 설정한다.
4. 오늘 기록 여부와 스트릭을 읽어 첫 예약 날짜를 결정한다.
5. 일일·필요 시 스트릭·주간 알림을 각각 예약한다.
6. 모든 필수 예약이 성공한 뒤에만 DB와 UI를 활성 상태로 갱신한다.

### 7.3 기록 저장

1. TodayController가 기록을 DB에 커밋한다.
2. 성공 상태를 UI에 반영한다.
3. 저널 변경 이벤트를 한 번 발생시킨다.
4. WidgetBootstrap은 이벤트를 받아 위젯 동기화와 ReminderCoordinator 재조정을
   각각 한 번 요청한다.
5. ReminderCoordinator는 저장된 설정과 오늘 기록을 읽어 일일·스트릭 알림을
   갱신한다. 오늘 기록이 있으면 첫 발생을 다음 날로 두며 주간 알림은 건드리지
   않는다.

알림과 위젯 후속 작업의 실패는 이미 성공한 저널 DB 커밋을 되돌리지 않는다.
오류는 기록하고 다음 앱 재개 또는 사용자 설정 변경에서 재시도한다.

## 8. 오류 처리와 상태 일관성

- 권한 거부: 예약과 설정 저장을 하지 않고 토글을 이전 상태로 유지한다.
- 시간대 확인 실패: UTC fallback 예약을 만들지 않고 실패를 반환한다.
- 일일 예약 실패: 활성화 또는 시간 변경을 실패 처리하고 설정을 저장하지 않는다.
- 보조 예약 실패: 이번 적용에서 새로 만든 예약을 정리하고 실패를 반환한다.
- 비활성화 중 취소 실패: UI를 성공으로 표시하지 않고 다시 시도할 수 있게 한다.
- 기록 저장 후 알림 재예약 실패: 기록은 유지하고 오류 로그를 남긴다.
- 위젯 동기화 실패: 마지막 성공 스냅샷을 바꾸지 않고 다음 요청에서 재시도한다.

플랫폼 API 오류를 서비스 내부에서 무조건 삼키지 않는다. 사용자 설정의 성공 여부를
결정해야 하는 호출은 실패를 상위 계층에 전달한다. 기록 저장 뒤 부가 작업처럼 핵심
커밋과 분리된 호출만 로깅 후 비차단 처리한다.

활성화, 비활성화, 시간 변경 중 일부 예약만 적용된 경우에는 DB에 남아 있는 이전
계획을 보상 적용한다. 보상 실패도 숨기지 않으며, 이후 설정 동작은 항상 DB의 계획을
기준으로 전체 재조정을 먼저 수행한다.

## 9. 테스트 및 검증

### 9.1 자동화 테스트

다음 회귀를 실제 저수준 어댑터 Fake를 통해 검증한다.

- 플러그인 초기화만으로 권한 요청이 발생하지 않는다.
- 사용자가 활성화를 요청했을 때만 권한 메서드가 한 번 호출된다.
- IANA 시간대가 `tz.local`에 적용되고 해당 현지 시각으로 예약된다.
- 시간대 식별자 오류는 UTC 예약이 아니라 실패가 된다.
- 예약 시각 이전·이후 및 `startTomorrow`의 첫 날짜가 정확하다.
- 일일 예약이 스트릭 및 주간 알림 ID를 취소하지 않는다.
- 시간 변경 뒤 주간 회고 알림이 유지된다.
- 오늘 이미 작성한 상태에서 활성화해도 다음 날 일일 알림이 존재한다.
- 기록 저장 뒤 설정 화면을 한 번도 열지 않았어도 저장된 설정으로 재예약한다.
- 기록 저장 뒤 주간 알림은 취소되지 않고 스트릭 알림은 다음 날로 이동한다.
- 오늘 기록 가져오기·삭제·전체 삭제 뒤 알림 계획이 현재 DB 상태와 일치한다.
- 예약 일부 실패 시 DB와 UI는 기존 설정을 유지하고 이전 예약 계획 복원을 시도한다.
- 동시에 들어온 시간 변경에서 마지막 요청이 최종 예약과 DB 상태가 된다.
- 저널 저장 한 번당 위젯 플랫폼 업데이트가 한 번만 발생한다.
- 동기화 도중 여러 요청은 최신 상태 기준 최대 한 번의 후속 실행으로 합쳐진다.
- 동일 위젯 스냅샷은 공유 저장소와 네이티브 업데이트를 생략한다.
- 실패한 위젯 스냅샷은 이후 호출에서 다시 시도된다.
